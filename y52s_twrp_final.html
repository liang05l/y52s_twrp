解密与「乱码」的判定（基于实测属性，不是推测）

本机是 FBE：ro.crypto.type=file、fileencryption=aes-256-xts、 ro.crypto.volume.filenames_mode=aes-256-cts（连文件名都加密）， gatekeeperd 运行中，vendor 侧有 Trustonic keymaster / gatekeeper。FBE 有两级密钥： DE（设备密钥，开机即可用，不需要密码）和 CE（凭证密钥，必须用锁屏 PIN / 图案 / 密码经 gatekeeper + keymaster 派生）。TWRP 要读到你的文件，必须走 CE 解密、也就是必须弹密码框让你输锁屏密码。

在 TWRP 里看到含义怎么办
弹出「输入密码 / Password」解密流程已启动，正常输入锁屏 PIN / 图案 / 密码（不是 Google 账号、不是另一个"加密密码"）；若设备只设了滑动解锁，TWRP 通常用默认密码自动解，不弹框
不弹密码框，/data 里是一堆乱码文件名只有 DE 密钥（或解密流程根本没跑），CE 密钥没派生；aes-256-cts 加密的文件名就显示成随机串不是数据丢了，也不是显示 bug。不要格式化 Data；回系统用 root 直接读 /data 是正常的
Decryption failed / Unable to mount /datakeymaster/gatekeeper 服务没起来，或密钥不匹配同上；不要点 Wipe / Format
/data 里是 DCIM、Download 等正常目录名CE 解密成功可正常备份与卡刷
为什么现在很可能不弹密码框：上游 BoardConfig.mk 没有 TW_INCLUDE_CRYPTO_FBE， system/bin/twrp 二进制可能根本没编译 FBE 解密代码——这决定它会不会发起密码输入流程。 已刷入的这版只修了「服务触发」与「gatekeeper 路径」，改不了二进制本身。 好消息是：系统里已实测 /data/media/0 有 95 个正常条目，数据完好；乱码只是 TWRP 没拿到 CE 密钥时的视图。

要确认到底属于哪一种，需要设备重新连上 USB（当前 adb / fastboot / PnP 都看不到设备）， 连上后我可以进 TWRP 读 recovery.log、mount 与解密相关属性再定。 若确认是二进制缺 FBE 支持，就只能用 twrp-10.0 源码树重编译，刷 ramdisk 解决不了。

17:45 最终结论：不是配置问题，是 TWRP 二进制没编译加密支持

用户反馈「没有输密码的界面」。改用 TWRP 自带命令行直接触发解密 twrp decrypt default_password，把输出按 UTF-8 解码，原文是：

正在尝试通过命令行解密 Data 分区或用户数据。 此版本不支持加密。

主程序是 /system/bin/recovery（2,207,880 B）；/system/bin/twrp 只是 11 KB 的命令行转发壳。 源码核对（TeamWin/android_bootable_recovery）：Decrypt_Device() 的解密实现、以及启动时设置 TW_IS_ENCRYPTED 并打开密码页的 Decrypt_Data()，都整段在 #ifdef TW_INCLUDE_CRYPTO 内； FBE 子路径还额外由 #ifdef TW_INCLUDE_FBE 保护；no_crypto_support=... 只出现在 #else 分支。 即这一版编译时没有定义这两个宏（不是缺一个配置文件）。这解释了全部现象：不弹密码框、GUI 无解密入口、命令行 decrypt 直接拒绝。

18.2 ccache 0.0 / 8.0（0.00%）的确切根因

不是缓存键写错，也不是 10 GB 额度问题，而是 Android 11 构建系统根本没启用 ccache。取回 TeamWin/android_build @ android-11 的 core/ccache.mk，原文：

# We no longer provide a ccache prebuilt. ...
# So if you still want to use ccache, continue setting USE_CCACHE, but also set
# the CCACHE_EXEC environment variable to the path to your ccache executable.
ifneq ($(CCACHE_EXEC),)
ifneq ($(filter-out false,$(USE_CCACHE)),)
  CCACHE_COMPILERCHECK ?= content
  CCACHE_SLOPPINESS := time_macros,include_file_mtime,file_macro
  CCACHE_BASEDIR := /
  CCACHE_CPP2 := true
  ifndef CC_WRAPPER
    CC_WRAPPER := $(CCACHE_EXEC)
  endif
  ...
endif
endif

原 workflow 只设了 USE_CCACHE=1，CCACHE_EXEC 为空 → 整段被跳过 → CC_WRAPPER 为空 → 一次编译都没经过 ccache，所以 ccache -s 恒为 0.0/8.0。修复：

  • 新增 CCACHE_EXEC=/usr/bin/ccache，并把 CC_WRAPPER / CXX_WRAPPER 一并导出为环境变量（Android 11 的 C++ 大多由 soong 编译，只读环境里的 wrapper）。

  • 新增「Configure ccache」步骤与构建步里的 get_build_var CC_WRAPPER 断言：wrapper 为空就直接失败，不再静默产出 0% 缓存；构建结束打印 ccache -s。
